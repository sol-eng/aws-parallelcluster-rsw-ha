AWS ParallelCluster

1 Deploying the cluster

Deploying the cluster brings everything together. parallelcluster/deploy.sh does the following:

  1. Reads your settings from an env file.
  2. Reads everything else from the Pulumi stack outputs.
  3. Renders the cluster template and the node scripts.
  4. Uploads the scripts to s3://<bucket>/<clustername>/.
  5. Runs pcluster create-cluster.

1.1 Prerequisites

  • The Pulumi stack is deployed (Pulumi). Its name is the cluster name.

  • A custom AMI is built (AMI), unless all sessions run in Apptainer containers (see When you need it).

  • The ParallelCluster CLI is installed. The version is pinned in the root pyproject.toml:

    uv sync                      # in the repository root
source .venv/bin/activate

  • aws, pulumi, jq and perl are on your PATH.

1.2 Deployment

cd parallelcluster
cp envs/demo.env.example envs/<clustername>.env
$EDITOR envs/<clustername>.env
./deploy.sh envs/<clustername>.env --dry-run   # render and validate only
./deploy.sh envs/<clustername>.env

envs/*.env files are ignored by git, so you can keep one per environment. The settings:

deploy.sh stops with an error if a Pulumi output is missing or a template contains a placeholder it can’t fill. The rendered files contain database passwords. After a real deployment they are deleted from tmp/; after --dry-run they stay there for inspection (delete them afterwards). Set KEEP_TMP=1 to keep them after a real deployment too.

When the cluster is up, ./cluster-stat.sh <clustername> prints the Workbench version, URLs and nodes. Add --show-secrets to also print the user password and the jump host SSH key.

1.3 The cluster templates

config/cluster-config-wb.default.tmpl defines:

  • Head node: t3.xlarge, 120 GB root volume, runs install-pwb-config.sh as OnNodeConfigured action. ParallelCluster’s internal shared storage is on encrypted EFS.
  • Slurm queues, all t3.xlarge except gpu, all running config-compute.sh on start:
    • interactive: 1 to 5 nodes, OverSubscribe=FORCE:2, for Workbench sessions
    • all: 0 to 10 nodes, for Workbench jobs and batch work
    • gpu: 0 to 5 g4dn.xlarge nodes
  • Login nodes: a pool of 2 t3.xlarge instances running Workbench
  • Shared storage: encrypted EFS for /home and /opt/rstudio
  • Directory service: SimpleAD from Pulumi via LDAP, with SSH keys generated for users
  • Slurm accounting in the Pulumi MySQL database

config/cluster-config-wb.easybuild.tmpl is the same, plus an existing EFS mounted at /opt/apps that holds an EasyBuild software stack.

Placeholders in the templates and scripts look like @@NAME@@. To add one, use it in a template and export a matching TPL_NAME variable in deploy.sh.

1.4 What runs where

Script Runs on When
scripts/install-pwb-config.sh head node OnNodeConfigured. Log: /var/log/install-pwb-config.log
scripts/config-compute.sh every compute node OnNodeConfigured. Log: /opt/rstudio/config-compute/<host>-<time>.log
scripts/config-login.sh every login node OnNodeConfigured. Log: /var/log/config-login.log

install-pwb-config.sh does the following:

  1. Downloads the Workbench package to /opt/rstudio/scripts. Packs the session components into a squashfs image, /opt/rstudio/session-components/rsw-session-<version>.sqsh (see Section 1.5).
  2. Writes the complete Workbench configuration to /opt/rstudio/etc/rstudio.
  3. Writes /opt/rstudio/scripts/rc.pwb, the restart helper for the login nodes (see Section 1.6).

It touches /etc/head-node, so rc.pwb can tell the head node apart from login nodes.

config-login.sh waits for that configuration, installs Workbench, activates the license (see Licensing) and copies the configuration to /etc/rstudio. It sets the node’s www-host-name to its EC2 private DNS name, mounts /scratch and starts rstudio-launcher and rstudio-server. Finally it installs pwb-lb.sh as the pwb-lb systemd unit, which registers the node with the ALBs and cleans up after replaced login nodes (see Keeping the load balancers in sync).

config-compute.sh mounts the session components image and /scratch.

1.5 Session components on squashfs

Compute nodes don’t download or extract the Workbench session components (about 800 MB as a tarball). The head node builds a zstd-compressed squashfs image of them once, on the shared /opt/rstudio EFS. Every compute node loop-mounts it read-only at /usr/lib/rstudio-server and adds the mount to /etc/fstab. This makes compute node start-up faster and guarantees that all nodes run identical session components.

  • The image is named after the Workbench version. Deploying a new PWB_VERSION builds a new image next to the old one.
  • It is written under a temporary name and then moved into place, so a node never mounts a partial image.
  • Compute nodes wait up to 30 minutes for the image to appear.
  • The mount uses threads=multi (parallel decompression) where the kernel supports it, otherwise plain ro,loop.

1.6 Changing configuration on a running cluster

Login nodes copy the shared configuration only once, when config-login.sh runs. To change the configuration:

  1. Edit the files in /opt/rstudio/etc/rstudio, so that login nodes added later get the change.
  2. Copy the changed files to /etc/rstudio on each running login node.
  3. Delete /opt/rstudio/workbench-<hostname>.state for each of those login nodes. config-login.sh registers rc.pwb as a cron job (every minute) on each login node, so within a minute rstudio-launcher and rstudio-server are restarted there. Its log is /var/log/rc.pwb.log.

2 Reaching full HA

The Workbench part of the setup is highly available: login node failures are tolerated and recovered, and all state is in PostgreSQL and on EFS. The remaining single point of failure is the head node: if it fails, Slurm stops working.

With all shared file systems on EFS, the head node is no longer an NFS server, so the difference between head and login nodes becomes much smaller. One could start additional slurmctld processes on the login nodes and add them to the Slurm configuration as backup controllers. This would also need regular checks that remove controllers that have disappeared. It is a moderate amount of additional logic, but it is another customisation to maintain.

A drawback: the ParallelCluster API (e.g. pcluster update-cluster) will very likely stop working when the head node is gone. Whether that matters for a production cluster is a separate question.
